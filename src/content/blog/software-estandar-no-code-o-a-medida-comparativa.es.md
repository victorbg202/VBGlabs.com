Para una pyme, la mejor solución no es necesariamente la más personalizada. El software estándar suele ser la primera opción cuando el proceso es común; el no-code o low-code encaja si hay que conectar herramientas o adaptar un circuito sin construir un producto entero; y el desarrollo a medida tiene sentido cuando el proceso es diferencial, estable y suficientemente valioso como para asumir su mantenimiento.

La decisión debe comparar el coste total, el encaje con el proceso, las integraciones, el control de los datos y la capacidad de cambio. Esta matriz te ayuda a hacerlo antes de pedir presupuestos.

## Las tres opciones, sin etiquetas comerciales

El **software estándar** es un producto ya creado para resolver una necesidad compartida: contabilidad, CRM, reservas, gestión de proyectos o atención al cliente. Normalmente se paga mediante suscripción y el proveedor mantiene la aplicación.

El **no-code o low-code** permite configurar flujos, formularios, bases de datos y automatizaciones con piezas existentes. “No-code” no significa que no exista trabajo técnico: hay que diseñar el proceso, definir permisos, gestionar errores y mantener las conexiones. La diferencia es que se escribe menos código propio.

El **software a medida** se desarrolla específicamente para el negocio. Puede ser una aplicación completa o únicamente la capa que falta entre sistemas existentes. Ofrece más control, pero también convierte las actualizaciones, la seguridad y la continuidad en responsabilidades que alguien deberá asumir.

Las opciones se pueden combinar. Una solución razonable puede utilizar un CRM estándar, automatizaciones configuradas y un pequeño componente propio para el proceso que realmente diferencia al negocio.

## Comparativa rápida

| Criterio | Software estándar | No-code / low-code | Desarrollo a medida |
| --- | --- | --- | --- |
| Puesta en marcha | Rápida si el proceso encaja | Media; requiere configuración y pruebas | Más lenta; hay que analizar y construir |
| Coste inicial | Bajo o moderado | Moderado | Alto |
| Coste recurrente | Suscripciones por usuario o uso | Suscripciones, operaciones y mantenimiento | Infraestructura, soporte y evolución |
| Adaptación | Limitada a las opciones del producto | Buena para flujos delimitados | Alta, dentro del alcance construido |
| Integraciones | Las ofrecidas por el proveedor | Muchas conexiones, con sus límites | Se pueden crear si hay API o acceso viable |
| Control de datos | Depende del contrato y la exportación | Repartido entre varias plataformas | Puede ser alto, pero debe diseñarse |
| Dependencia | Del proveedor principal | De varias herramientas y conectores | Del equipo, la documentación y la tecnología |
| Mantenimiento interno | Bajo | Medio | Alto |

La tabla no ofrece un ganador automático. Un coste inicial bajo puede acabar siendo caro con treinta usuarios, muchos complementos o trabajo manual residual. Una aplicación a medida puede durar años o convertirse en un sistema difícil de mantener si no tiene responsable, pruebas y documentación.

## La matriz de decisión en cinco criterios

Puntúa cada criterio de **0 a 3**. No se busca una precisión matemática; el objetivo es que el equipo explique por qué necesita una opción u otra.

### 1. Encaje del proceso

- **0:** es un proceso habitual y podemos adaptarnos a una herramienta conocida.
- **1:** necesitamos algunos campos, reglas o informes propios.
- **2:** el circuito tiene varias excepciones que aportan valor real.
- **3:** el proceso es diferencial y una herramienta genérica eliminaría esa ventaja.

### 2. Integraciones necesarias

- **0:** puede funcionar de manera independiente.
- **1:** solo requiere importar o exportar archivos.
- **2:** debe sincronizarse con dos o tres sistemas mediante API.
- **3:** coordina varios sistemas en tiempo real y los errores tienen impacto operativo.

### 3. Datos, permisos y trazabilidad

- **0:** datos poco sensibles y permisos sencillos.
- **1:** roles básicos e historial de cambios.
- **2:** separación estricta por clientes, sedes o equipos.
- **3:** requisitos específicos de auditoría, residencia, conservación o control de acceso.

Una puntuación alta no obliga a desarrollar. Primero comprueba si un producto sectorial ya cubre esos requisitos mejor que un proyecto nuevo.

### 4. Ritmo de cambio

- **0:** el proceso todavía cambia cada semana.
- **1:** conocemos el objetivo, pero no todas las reglas.
- **2:** el proceso es estable y las excepciones están documentadas.
- **3:** existe volumen, un responsable y datos para validar el resultado.

Aquí la lectura es diferente: una puntuación baja favorece una prueba configurable, no una gran construcción. Desarrollar sobre un proceso inestable convierte cada aprendizaje en una modificación costosa.

### 5. Impacto económico y estratégico

- **0:** se utiliza poco y el problema tiene un coste bajo.
- **1:** ahorra tiempo, pero no bloquea el negocio.
- **2:** afecta cada día a varios usuarios o clientes.
- **3:** limita ventas, capacidad, calidad o un servicio diferencial.

Para calcular este apartado con datos, utiliza la [calculadora del coste de una tarea manual](/es/blog/calcular-coste-tarea-manual-automatizar/). Incluye tiempo, errores, supervisión y mantenimiento; no solo el precio de la licencia.

## Cómo interpretar el resultado

Suma los cinco criterios, con un máximo de 15 puntos:

- **0–4 puntos: empieza con software estándar.** Configura lo mínimo, prueba el circuito real y evita personalizar hasta que aparezca una limitación medible.
- **5–9 puntos: explora una solución configurada o híbrida.** Una herramienta estándar con automatizaciones o una capa no-code puede cubrir el hueco sin asumir un producto completo.
- **10–15 puntos: valora el desarrollo a medida.** No es una orden de compra. Es la señal para realizar un análisis funcional, estimar el coste total y compararlo con productos sectoriales.

Hay tres condiciones que pueden invalidar la puntuación. Si el proceso no tiene responsable, si nadie puede definir qué es un resultado correcto o si no existe presupuesto de mantenimiento, aún no es el momento de construir. La guía sobre [qué vale la pena automatizar en una pyme](/es/blog/que-vale-la-pena-automatizar/) ayuda a revisar esa base.

## Ejemplo: gestionar solicitudes de clientes

Imaginemos una empresa que recibe solicitudes por formulario, correo y teléfono. Dos personas las clasifican, piden la información que falta y crean tareas en el gestor interno.

Si solo necesita centralizar entradas, asignar responsables y ver el estado, probablemente ganará un sistema estándar de tickets o CRM. Si ya dispone de las herramientas, pero falta conectar el formulario, avisar al equipo y crear tareas, una automatización no-code o low-code puede bastar.

El desarrollo a medida empieza a tener sentido si la clasificación determina un proceso propio, existen reglas complejas por cliente, hay que separar datos entre organizaciones y el volumen justifica una interfaz específica. Incluso entonces, puede ser mejor conservar el CRM y desarrollar únicamente el módulo diferencial.

## Calcula el coste total, no solo el primer año

Compara las alternativas en un horizonte de tres años e incluye:

- configuración, migración y limpieza de datos;
- licencias por usuario, volumen u operación;
- integraciones y complementos;
- formación y tiempo de adaptación;
- supervisión de las automatizaciones;
- correcciones, actualizaciones y seguridad;
- exportación de datos o cambio de proveedor;
- horas internas que el nuevo sistema seguirá necesitando.

Pide además una demostración con dos casos reales y una excepción difícil. Una presentación preparada enseña el camino ideal; una prueba con tus datos descubre el encaje, los permisos, los errores y los pasos manuales que permanecen.

## Checklist antes de decidir

No apruebes la compra o el desarrollo hasta poder responder:

- qué problema concreto resuelve y cómo se medirá;
- quién es responsable del proceso y de la herramienta;
- qué datos entran, dónde se guardan y cómo se exportan;
- qué sistemas deben conectarse;
- qué excepciones requieren revisión humana;
- qué ocurre si falla una integración;
- cuánto costará durante tres años;
- quién realizará el mantenimiento;
- cómo se probará la solución con un alcance reducido;
- en qué situación se decidirá detenerla o sustituirla.

La mejor decisión suele ser la solución más pequeña que resuelve bien el problema y permite aprender. Si necesitas comparar opciones sin empezar por una tecnología concreta, una [consultoría tecnológica](/es/consultoria/) puede convertir el proceso, los costes y los riesgos en un alcance verificable antes de invertir.
